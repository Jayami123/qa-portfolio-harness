## D-HAR-B3: Cal catcher in its own overlay, on loopback ports 1026 and 8026

- Context: `up cal` composes the fork's `docker-compose.yml` with `docker/cal.compose.yml` and `docker/cal.redis.compose.yml`. The brief asks for no change to upstream product defaults.
- Options considered: (a) add the service to `docker/cal.compose.yml`; (b) a new overlay `docker/cal.mail.compose.yml`, listed in `composeOpts`.
- Choice: (b). Ports `127.0.0.1:1026:1025` and `127.0.0.1:8026:8025`.
- Reason: follows the Redis overlay pattern, and leaves the existing Cal overlay untouched. 1026 and 8026 do not collide with Cal 3000, 5555, 5450, 6381, Documenso 3001, 5451, 2525, 9003, Twenty 3002, 5434, 1025, 8025, Medusa 9000, 8000, 5433, or Redis 6380.
- Evidence: `src/adapters/cal-mail.test.ts` "neither host port collides with another product or Redis" and "every published port binds 127.0.0.1". `src/adapters/cal.adapter.ts` `composeOpts` lists `cal.mail.compose.yml`.

## D-HAR-B4: SMTP rewrite only as a pair, only from example defaults, to 127.0.0.1

- Context: the fork ships `EMAIL_SERVER_HOST='localhost'` (quoted) and `EMAIL_SERVER_PORT=1025` (`/home/user/products/cal/.env.example:227-228`). The root `.env` writer (`ensureCalRootEnv`) previously wrote only generated secrets. Port 1025 is Twenty's Mailpit.
- Options considered: (a) rewrite each key on its own; (b) rewrite the pair only when both keys are missing or still the example value; (c) rewrite to `localhost`.
- Choice: (b), with host `127.0.0.1`.
- Reason: rewriting one key alone could pair a real host with the catcher's port, or the reverse. Rewriting only the pair keeps a real configuration intact. `127.0.0.1` rather than `localhost`, because the catcher binds IPv4 loopback only, and `localhost` can resolve to `::1`.
- Evidence: `src/adapters/cal-env.ts` `smtpIsExampleDefault`; tests in `src/adapters/cal-env.test.ts` "ensureCalRootEnv SMTP routing" (7 cases, including the "never overwrites a real host" and "never overwrites a real port" cases).

## D-HAR-B6: rate-limit keys forwarded from the harness environment, no harness default

- Context: `buildCalApiEnv` (`src/adapters/cal-api-env.ts`) built the API spawn env from named keys only, and `apiSpawnEnv` inherits only `NODE_OPTIONS` and telemetry from the harness env (`cal.adapter.ts` `calHeapEnv`). So the rate-limit keys were never forwarded. The fork reads `RATE_LIMIT_DEFAULT_LIMIT_API_KEY` with fallback 120 (`apps/api/v2/src/lib/throttler-guard.ts:34-36`, `apps/api/v2/src/env.ts:25-26`) and `RATE_LIMIT_DEFAULT_TTL_MS` with fallback 60000.
- Options considered: (a) forward when set and validate; (b) set a harness default of 120; (c) read the value from the root `.env`.
- Choice: (a). Blank counts as unset. An invalid value (not a positive whole number) throws `…must be a positive whole number…` naming the key, never the value. The helper `calApiKeyRateLimit()` reads the same env and throws by name when unset.
- Reason: the brief says never to set a guessed default, and never to report 120 as effective without the harness having set it. Only the harness process env is read, the same source the spawn uses.
- Evidence: `src/adapters/cal-api-env.ts` `CAL_RATE_LIMIT_KEYS`, `readRateLimitValue`, `calApiKeyRateLimit`. Tests: `src/adapters/cal-api-env.test.ts` "rate-limit forwarding into the API spawn env" (7 cases) and "calApiKeyRateLimit" (4 cases). `describeCalApiEnv` shows the forwarded values as `<redacted>`.
