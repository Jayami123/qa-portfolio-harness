## 5 Architecture

Processes started by `up cal`, in order:

1. Compose project `qa-harness-cal`. Files: product `packages/prisma/docker-compose.yml`, `docker/cal.compose.yml` (Postgres 5450), `docker/cal.redis.compose.yml` (Redis 6381, new), plus pg-stats overlay when enabled.
2. Seed (unchanged).
3. Cal web on `127.0.0.1:3000`. Pid `.harness/cal-web.pid` (unchanged).
4. Cal API v2 on `127.0.0.1:5555`. Pid `.harness/cal-api.pid` (new). Started after the web only if the web is healthy or after the web start; the order does not matter for correctness, but the readiness gate needs both.

Process tree for the API (POSIX): `node dist/apps/api/v2/src/main.js`, detached, process group id = pid. Windows: `taskkill /T /PID <pid>`, same as the web.

Env of the API process (spawn env, not a file):

- inherited: `process.env` (spawn merge, `spawn-detached.ts:46`).
- added: `API_PORT=5555`, `REDIS_URL=redis://127.0.0.1:6381`, `NODE_OPTIONS` from `calHeapEnv(process.env)`, `NEXT_TELEMETRY_DISABLED=1`.
- copied from the product root `.env` (parsed with `dotenv` in memory, never printed, never written to a harness file): `DATABASE_URL`, `DATABASE_READ_URL`, `DATABASE_WRITE_URL`, `DATABASE_DIRECT_URL`, `NEXTAUTH_SECRET`, `CALENDSO_ENCRYPTION_KEY`, `JWT_SECRET`, `CALCOM_SERVICE_ACCOUNT_ENCRYPTION_KEY`. The list is taken from `apps/api/v2/.env.example:2` and `:9-30`, and the builder confirms each name against the config schema in its first run.
- The API's own `.env.example` values are NOT copied. Its `JWT_SECRET` and keys are example values.

Cwd of the API process: `<products>/cal/apps/api/v2`. No `.env` file is created there. `dotenv/config` (`main.ts:1`) loads `.env` from cwd if present, and never overrides a variable already set, so the spawn env wins.

Redis: `docker/cal.redis.compose.yml` with `redis:7`, `127.0.0.1:6381:6379`, healthcheck `redis-cli ping`. It runs in the same compose project as Postgres, so `down` removes it.

### 6.1 `src/internal/node-options.ts` (new)

```ts
/** Node flag names for the old-space limit. Node takes both spellings in NODE_OPTIONS. */
const HEAP_FLAG = /(^|\s)--max[-_]old[-_]space[-_]size(=|\s|$)/;

/**
 * Returns NODE_OPTIONS with a default heap limit. The caller's own limit wins and is returned unchanged.
 * Otherwise the default is appended after the caller's flags, which are kept. A blank input returns the default alone,
 * so an empty NODE_OPTIONS gives the same value as v0.2.18.
 */
export function withHeapDefault(current: string | undefined, defaultMb: number): string {
  const base = current?.trim() ?? "";
  const flag = `--max-old-space-size=${String(defaultMb)}`;
  if (base === "") {
    return flag;
  }
  if (HEAP_FLAG.test(base)) {
    return base;
  }
  return `${base} ${flag}`;
}
```

Unit tests (`src/internal/node-options.test.ts`, new):

```ts
async up(): Promise<void> {
  // ... existing product-file checks (unchanged)
  await composeUp(this.composeOpts(), { wait: true, waitServices: [CAL_POSTGRES_SERVICE, CAL_REDIS_SERVICE] });

    this.verifyListenerIsRecorded();         // web pid check (existing)
    this.verifyApiListenerIsRecorded();      // api pid check (new)
    console.log(`Cal already healthy: web ${this.webRootUrl()}, API ${this.cfg.apiBaseUrl}/health`);
    return;
  }
  if (state.web === "down") { await this.startWeb(); }  // existing web start code, moved into a method, no behaviour change

  await this.waitForWeb(logFile, timeoutMs);            // existing
  await this.waitForApi(apiLogFile, CAL_API_WAIT_MS);   // new
```

#### 6.4.1 Foreign listener message

`foreignListenerMessage` (new, pure, unit tested): `Port ${port} is held by pid ${pid} (${exe}), which is not the recorded ${name} process. Stop it yourself, then run up again. The harness does not kill processes it did not start.` The pid and executable come from `listenerPids` and the existing Windows/Linux helpers (`proc-net-listeners.ts`).

`startApi()` (new):

1. `ensureApiBuild()`: build only when `.harness/cal-api-build.json` (`HarnessBuildRecord`, existing interface at `cal.adapter.ts:25`) does not match the fork's HEAD, or `dist/apps/api/v2/src/main.js` is missing. Build commands run with `calHeapEnv(process.env)` and timeout `CAL_API_BUILD_MS`:
   - `yarn workspace @calcom/platform-constants build`, `@calcom/platform-enums`, `@calcom/platform-utils`, `@calcom/platform-types`, `@calcom/platform-libraries` (these are the chain in `apps/api/v2/package.json` `build:docker`), then `yarn workspace @calcom/trpc build:server`, then `yarn workspace @calcom/api-v2 build`.
   - Use the same yarn resolver the web uses (`resolveYarn()`).
   - The builder confirms the exact command list against `build:docker` at the pinned SHA. Record the time of each step.
2. Refuse to start when the fork has no `node_modules` at the API dir or root (same error style as `up()` lines 396-404).
3. Read the root `.env` in memory (`dotenv.parse`), take the listed keys (section 5), and build the spawn env. Missing key: throw `Cal API v2 needs <KEY> in <products>/cal/.env` (names only, no value).
4. `calApiSpawnSpec` → `spawnLogged(spec.command, spec.args, { cwd: apiDir, logFile: .harness/cal-api.log, env: {...apiEnv}, detached: true, shell: false })`.
5. `writeCalApiPid(pid)`; `unref()`; wait 8 s; if `exitCode !== null`, throw `Cal API v2 exited immediately (code N). Last log:\n<tail>`.

`waitForApi(logFile, timeoutMs)`: poll `${apiBaseUrl}/health` every 5 s with the existing `pollHealth` (`timeoutMs`, `requestTimeoutMs: 180_000`, as `waitForWeb` does). On timeout throw `Timed out waiting for <url>` with the API log tail (same format as `waitForWeb`, `cal.adapter.ts:421-431`). This is the "API log tail" required by the negative check.

`down()` (line 539) new order: stop the API, then the web, then compose down (which removes Redis).

```ts
async down(): Promise<void> {
  await this.stopApi();   // new: calApiStopDeps, same rules as stopWeb (process group or taskkill /T, start mark, port wait)
  await this.stopWeb();   // existing
  await composeDown(this.composeOpts());
  console.log("Cal API v2 and web stopped; compose stack (Postgres, Redis) torn down.");
}
```

If `stopApi` throws (port held by a live recorded pid), `down()` throws and does not run compose down. That matches `stopWeb` behaviour.

Unit tests (`cal.adapter.test.ts`, new cases using fake deps; no network):

- `readyState` with fake probes: `(ok, ok)` returns early and does not start anything.
- `(ok, down)` starts only the API. `(down, ok)` starts only the web. `(down, down)` starts both.
- `(foreign, ok)` and `(ok, foreign)` throw a message that names the port and the pid.
- `down()` calls stop API before stop web and before compose down (order list).

### 6.6 `src/adapters/twenty-passthrough.ts` (new, HR-2)

```ts
/** Variables the harness forwards to Twenty server and worker by name. Values come from the caller's env and are never written to disk. */
export const TWENTY_PASSTHROUGH_ENV = [
  "OUTBOUND_HTTP_ALLOWED_INTERNAL_HOSTS",
  "IS_BILLING_ENABLED",
  "BILLING_STRIPE_API_KEY",
  "BILLING_STRIPE_WEBHOOK_SECRET",
  "BILLING_STRIPE_PUBLISHABLE_KEY",
] as const;

export type TwentyPassthroughName = (typeof TWENTY_PASSTHROUGH_ENV)[number];

/** The names set to a non-blank value in env, in allowlist order. Blank or whitespace is unset. */
export function readTwentyPassthroughNames(env: NodeJS.ProcessEnv): TwentyPassthroughName[] {
  return TWENTY_PASSTHROUGH_ENV.filter((name) => {
    const raw = env[name];

  });
}
```
