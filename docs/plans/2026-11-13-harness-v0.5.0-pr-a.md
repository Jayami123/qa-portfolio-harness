## D-HAR-B1: env schema stays a full parse

- Context: `loadConfig` parses all of `process.env` with `envSchema` (`src/config.ts:171`). The bug is the filesystem root check, not env validation.
- Options considered: (a) keep the full `envSchema.parse` and make only the root existence check lazy; (b) split the zod schema per product so each product validates only its own keys.
- Choice: (a).
- Reason: a split changes what an invalid env value fails on, for every consumer, and makes the fix bigger than the bug. The full parse only checks values, not the filesystem, so it does not block single-product runs. Fail closed stays: a typo in any product's URL still fails loudly.
- Evidence: `src/config.ts:171`, `src/config.ts:27-102`.

## D-HAR-B2: `loadConfig()` stays eager

- Context: `loadConfig()` is internal to the package but is the function the existing tests and any consumer call to get the full `HarnessConfig`. The brief allows changing it only if the existing tests stay green.
- Options considered: (a) keep `loadConfig()` eager, unchanged; (b) make it return a partial config.
- Choice: (a).
- Reason: the full `HarnessConfig` shape is a contract. Eager loading is correct for "give me everything". The single-product callers (`getAdapter`, `getProductConfig`) move to a new lazy path. The four-dir stubs in `config.test.ts` keep working unchanged.
- Evidence: `src/config.ts:166-240` (unchanged); `src/config.test.ts:17-62` (existing tests unchanged).

## D-HAR-B3: new lazy helper, no cache write, not re-exported from the index

- Context: `up`, `down` and `smoke` need one product's config. `src/index.ts` re-exports only `getAdapter` from the registry and `documensoMailApiUrl` from config.
- Options considered: (a) `loadProductConfig(id)` exported from `config.ts` only, returning `HarnessConfig[K]`, and used by `getProductConfig` and `getAdapter`; (b) also re-export it from `src/index.ts`; (c) populate the shared `cached` on each lazy call.
- Choice: (a). It does not write the shared cache, because the cache holds the full `HarnessConfig` and a partial write would be wrong. It is not re-exported, so the public API is unchanged.
- Reason: keeps public exports stable, as the brief requires. A partial cache would make a later `loadConfig()` return stale partial data.
- Evidence: `src/index.ts:1-22`.
